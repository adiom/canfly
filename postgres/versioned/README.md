# Версионированные SQL-миграции Canfly

[Baseline 0000](../baseline/README.md) описывает структуру production от 19.11.2026. Новая история стартует с `0001_<описание>.sql` в этом каталоге. Исторические SQL-файлы лежат в `postgres/` и `postgres/migrations/`.

## Команды

| Команда | Действие |
| --- | --- |
| `pnpm db:migrate:status` | Показывает состояние baseline, список ожидающих и время применения записанных версий. |
| `pnpm db:migrate:verify` | Проверяет непрерывность журнала, имена и SHA-256 применённых файлов. До первой миграции после `0000` также сверяет 14 категорий структуры по production-манифесту. Ожидающие миграции отображаются в выводе. |
| `pnpm db:migrate:baseline --confirm=<цель>` | Регистрирует существующую схему. До записи сверяет каталог с манифестом в той же транзакции. Повтор проверяет историю и возвращает существующий результат. |
| `pnpm db:migrate:up --confirm=<цель>` | После регистрации baseline применяет ожидающие версии по порядку. |

Для всех команд задайте `CANFLY_MIGRATION_DATABASE_URL` в окружении процесса. Поддерживаются PostgreSQL 17 на `127.0.0.1:<порт>/canfly_e2e_*` и прямой TLS endpoint базы `canfly_tests` в проекте Neon `canfly-db-tests` (`muddy-heart-67237859`). CLI сверяет имя базы на сервере. Для записи параметр `--confirm` должен совпасть с разрешённой целью. Для локальной базы это `127.0.0.1:<порт>/<имя>`, для Neon — `<прямой hostname>/canfly_tests`. При смене тестового endpoint сначала подтвердите его принадлежность проекту и обновите разрешённый hostname в коде.

Журнал `canfly_migrations.schema_migrations` хранит версию, имя файла, SHA-256 точных байтов SQL и время записи `timestamptz`. PostgreSQL удерживает сессионную advisory lock с ключом `4865638142842026000` на одном прямом соединении на протяжении команды. Если ключ занят, команда завершится с ошибкой. Сверка непосредственно перед регистрацией выполняется в `REPEATABLE READ`. На время регистрации исключите отдельные сеансы с DDL, поскольку advisory lock координирует только клиентов, использующих этот ключ. Сверка использует границы [исходного каталога](../baseline/README.md). После применения новых версий `verify` подтверждает историю по файлам. Для проверки структуры после обновления опишите ожидаемый результат в тесте миграции.

## Добавление миграции

1. Добавьте один UTF-8 SQL-файл следующей версии с четырьмя цифрами и именем из строчных латинских букв, цифр и подчёркиваний. Используйте последовательные номера и окончания строк LF. Первый реальный файл получит номер `0001`.
2. Пишите серверный SQL, допустимый внутри транзакции. CLI исполняет его через PL/pgSQL и записывает версию в той же транзакции. Управление транзакцией и команды клиента `psql` в файле недопустимы. Учитывайте, что PostgreSQL сохраняет продвижение последовательностей при откате. Для SQL с внешними эффектами требуется отдельная процедура. При ошибке текущая миграция откатывается, а успешно завершённые версии сохраняются.
3. Проверьте обновление с baseline и повторный `up`. Оставляйте применённый файл побайтово неизменным. Исправление применённой версии публикуйте следующим номером.

## Нетранзакционный DDL

Для операции вроде `CREATE INDEX CONCURRENTLY` подготовьте проверяемый SQL для ручного запуска в отдельном каталоге вне `postgres/versioned/`. В очередную версию добавьте транзакционную проверку результата. Она должна выдавать ошибку, пока результат отсутствует или отличается от ожидаемого. Для индекса сверяйте схему, таблицу, определение, а также `pg_index.indisvalid` и `indisready`. Оба файла проходят ревью вместе. Для такой версии добавьте отдельный шаг выполнения DDL в CI на одноразовой базе перед попыткой записать эту версию.

1. Зарегистрируйте baseline, запустите `status` и `verify`, убедитесь, что проверяющая версия будет следующей в очереди. Согласуйте отдельный запуск DDL на проверенной тестовой цели.
2. Откройте один сеанс `psql -X` к прямому тестовому endpoint с проверкой TLS и вводом пароля по запросу. Сверьте `\conninfo` и `SELECT current_database()`. Включите `\set ON_ERROR_STOP on` и `\set AUTOCOMMIT on`, затем в этом же сеансе получите блокировку командой `SELECT pg_try_advisory_lock(4865638142842026000::bigint);`. Продолжайте только при результате `t`. В этом же сеансе проверьте последнюю версию в журнале, затем выполните один согласованный DDL через `\i <путь>` без блока транзакции.
3. При сбое сверьте фактическое состояние объекта под той же блокировкой. Например, конкурентное построение может оставить невалидный индекс. Очистку или повтор выполняйте после проверки состояния и отдельного согласования. По завершении закройте сеанс для освобождения блокировки. Запустите обычный `up`. Он выполнит проверку результата и внесёт её версию в журнал. При ошибке проверки очередь остановится.

## Neon и fish

В Neon Console откройте проект `muddy-heart-67237859`, выберите базу `canfly_tests`, отключите pooling в диалоге Connect и скопируйте прямой URI. Вставьте его только в скрытый запрос `read`. Команды читают URI из окружения своего процесса. Переменная ниже локальна для блока fish.

```fish
begin
    read --silent --local --export --prompt-str 'Прямой URI canfly_tests: ' CANFLY_MIGRATION_DATABASE_URL
    and pnpm db:migrate:status
    and pnpm db:migrate:verify
    and pnpm test:db:migrations:neon
end
```

Тест Neon выполняет чтение каталога и журнала и кратковременно проверяет advisory lock на двух соединениях. После отдельного разрешения на регистрацию и применение SQL выполните следующий блок. Проверьте список ожидающих версий перед запуском `up`.

```fish
begin
    set -l target ep-ancient-feather-bbgnicrs.c-15.us-east-1.aws.neon.tech/canfly_tests
    read --silent --local --export --prompt-str 'Прямой URI canfly_tests: ' CANFLY_MIGRATION_DATABASE_URL
    and pnpm db:migrate:verify
    and pnpm db:migrate:baseline --confirm=$target
    and pnpm db:migrate:up --confirm=$target
    and pnpm db:migrate:up --confirm=$target
    and pnpm db:migrate:verify
    and pnpm db:migrate:status
end
```

## GitHub Actions

[Workflow PostgreSQL 17](../../.github/workflows/postgres-baseline.yml) восстанавливает baseline в одноразовых PostgreSQL 17.12 и выполняет существующие тесты прикладных репозиториев. Затем CI регистрирует baseline, применяет очередь SQL, повторяет `up` и сверяет журнал. На отдельной чистой базе `canfly_e2e_migration_system` он проверяет отказ при расхождении каталога, конкурентный запуск, частичный откат, повтор и подмену уже применённого файла. Интеграционный тест использует SQL-фикстуры во временном каталоге и требует отдельный локальный URL в `CANFLY_MIGRATION_TEST_DATABASE_URL`. Без него `pnpm test:db:migrations` запускает проверки, которым база не требуется.

# Безопасный рефакторинг Canfly

Сначала прочитай [AGENTS.md](../../../AGENTS.md). При запросе только на аудит составь список кандидатов без правок. Для многоэтапной работы используй [шаблон ExecPlan](../../../docs/refactor/EXECPLAN.template.md).

## Существующие Skills

Подключай по затронутой области:

- [canfly-architecture](../canfly-architecture/SKILL.md) — точки входа и границы модулей.
- [canfly-data-access](../canfly-data-access/SKILL.md) — SQL, модели данных и транзакции.
- [canfly-guardrails](../canfly-guardrails/SKILL.md) — доступ, маршруты, MCP и побочные эффекты.
- [canfly-e2e](../canfly-e2e/SKILL.md) — выбор проверок, фикстур и безопасной среды.
- [next-dev-loop](../next-dev-loop/SKILL.md) — проверка изменённого поведения UI и серверных сценариев в изолированном Next.js runtime.

## Границы

Без отдельного разрешения сохраняй публичные API и контракты MCP, маршруты, авторизацию, схему БД, SEO, форматы опубликованных изданий и алгоритмы сохранения прогресса чтения и текстовых якорей. Обновления зависимостей и миграции фреймворка выноси в отдельные задачи.

Удаляй код только при подтверждённом отсутствии потребителей. Помимо статического поиска и реэкспортов, проверь применимые динамические импорты и маршруты App Router, proxy и rewrites, cron, регистрацию MCP, файловые ресурсы, ссылки из БД и настроек, старые сохранённые данные и внешние вызовы. При неопределённости оставь код и зафиксируй недостающие доказательства.

## PostgreSQL

- `postgres/schema.sql` и файлы миграций описывают историю репозитория. Для SQL сверяй [фактическую схему целевого окружения](../../../docs/architecture/postgresql-schema-drift.md) и контракт запроса, включая типы, сортировку, кардинальность, `NULL` и права доступа. Без этих сведений останови опасный проход и запиши неопределённость в ExecPlan.
- Отсутствие таблицы или колонки в одном окружении не доказывает ненужность кода. Сохраняй fallback совместимости схем до отдельной задачи. Перед предложением удалить предположительно неиспользуемый SQL-объект проверь зависимости в каталоге, вызовы из кода и внешних клиентов.
- Выноси функциональные исправления в отдельные задачи. Не применяй миграции автоматически и не выполняй DDL/DML в production в рамках рефакторинга.

## Один проход

1. Зафиксируй исходный SHA и локальные правки. Найди точки входа и опиши наблюдаемое поведение. Для каждого кандидата укажи файл и символ, причину, риск и способ проверить паритет. При сравнении похожих веток проверь входы, ошибки, порядок эффектов и крайние случаи.
2. Выбери одно изменение, которое можно проверить и откатить отдельно. При разделении крупного компонента сохрани границы Server/Client и жизненный цикл состояния и эффектов. При модернизации проверь семантику замены по локальной документации установленной версии.
3. До правки прогони минимальную проверку текущего поведения. Для сохранения контракта добавь недостающую проверку, проходящую на исходном коде. При исправлении бага обязателен регрессионный тест: воспроизведи дефект и проверь причину падения (Red), внеси минимальное исправление (Green), затем при необходимости упрости код с повторным прогоном (Refactor). Для проверок с побочными эффектами используй среду, предусмотренную canfly-e2e.
4. После правки повтори проверку в той же среде, проверь diff и выполни применимые проверки AGENTS.md. Запиши команды, результаты и пропуски. При расхождении или невозможности подтвердить существенный инвариант останови проход и пересмотри изменение. Если нужен откат, ограничь его диффом этого прохода и сохрани чужие правки.

Начинай с адресного поиска и читай только затронутые модули, их прямых потребителей и релевантные тесты.

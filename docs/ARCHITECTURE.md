# Архитектура чтения и статистики Canfly

Точка входа в базу знаний: [docs/architecture/README.md](architecture/README.md). Код чтения повторно сверён на `7a2b84d629335d9d2e8f037a798464911177ca54` (10.11.2026); описанные ниже наблюдения по схеме относятся к тестовой Neon на 06.11.2026 и не подтверждают её текущее состояние.

Проверено по коду текущей рабочей копии и структуре `neondb` проекта Neon `test-canfly` (`round-surf-75113507`, ветка `main`). Это тестовая база с копией структуры без production-данных. Поведение на реальном трафике и содержимое production-БД этим аудитом не проверены. Исторические SQL-файлы не считаются линейной историей создания этой базы.

## Карта маршрутов и данных

| Маршрут | UI | API / Action | Серверные модули и SQL | Таблицы |
| --- | --- | --- | --- | --- |
| `/release/[slug]` | страница релиза, ссылки на издания | нет события просмотра | `fetchReleaseBySlug`, `fetchEditionsByRelease` и связанные выборки | `releases`, `editions`, `chapters`, связи релиза |
| `/vvvvv/[slug]`, книга/журнал | `SpreadReader` | `POST /api/reading-progress` | `fetchEditionByIdOrSlug`, `fetchPublishedChaptersByEdition`, `fetchReadingProgress`, `upsertReadingProgress` | `editions`, `releases`, `chapters`, `reading_progress`, `chapter_highlights` |
| `/vvvvv/[slug]`, комикс | `ReleaseComicReader` | нет записи прогресса | выборка издания и глав | `editions`, `releases`, `chapters` |
| `/vvvvv/[slug]`, аудио | `ReleaseAudioPlayer` | нет записи прогресса | выборка издания и глав | `editions`, `releases`, `chapters` |
| `/vvvvv/[slug]`, artwork | `ArtworkViewer` | нет записи прогресса | выборка издания и релиза | `editions`, `releases` |
| `/user` и `/user/[slug]` | `ReadingShelf` | только чтение | `fetchShelf`, `fetchReaderProfileSummary` | `reading_progress`, `chapters`, `editions`, `releases`, `users`, `chapter_highlights` |
| `/studio` | `ReleaseCard`, сводка | `getMyReleasesWithEditions` | `listAllReleasesWithEditions` / `listReleasesByAuthorWithEditions` | `releases`, `editions`, `release_collaborators` |

`lib/db.ts` создаёт пул `pg`; отдельных ORM-моделей нет. Маршрут ридера проверяет публикацию релиза и издания, выбирает компонент по `edition.format`. Для книги начальная глава берётся из последней записи `reading_progress`; для комикса и аудио этот путь не используется. `reading_progress` — одна обновляемая запись на пользователя, издание и главу. Это состояние прогресса, а не журнал каждого посещения.

## Что записывается

| Событие | Фактическое поведение |
| --- | --- |
| Перелистывание книги/журнала авторизованным пользователем | Клиент через 1,5 с посылает `POST /api/reading-progress`; сервер делает `INSERT ... ON CONFLICT DO UPDATE` для процента и `last_read_at`. Локально также сохраняется якорь в `localStorage`. |
| Закрытие или скрытие вкладки книги | Клиент повторно посылает последний payload с `keepalive`; подтверждения доставки не ожидает. |
| Чтение гостем | Записи в БД нет; API требует `getCurrentUser()`. |
| Комикс, аудио, artwork | Прогресс визуализируется локально, но запрос к API прогресса из этих компонентов не выполняется. |
| Открытие релиза или главы | В коде страниц нет вызова обновления `view_count`. Функция `incrementChapterViews` существует, но вызовов у неё нет. Записи просмотров релиза также не обнаружено. |
| Профиль и Studio | Читают уже накопленные `reading_progress` и `releases.view_count`; просмотр этих страниц сам по себе не создаёт события. |

## Подтверждённые неисправности, по приоритету

1. **P0 — точная позиция не сохраняется в тестовой схеме.** `SpreadReader` отправляет `position`, а `lib/server/reading-progress.ts:supportsPosition` проверяет наличие колонки и без неё исключает поле из `INSERT`. В снимке тестовой `public.reading_progress` от 06.11.2026 колонки `position` нет; текущее состояние требуется проверить отдельно. После перехода на другое устройство остаются только глава и процент; `localStorage` работает лишь в том же браузере. Нужна сверенная миграция добавления `position jsonb`, проверка формата и явный контракт API вместо бесшумного fallback.
2. **P0 — счётчики просмотров не пополняются.** В `releases` и `chapters` имеются `view_count integer DEFAULT 0`. `lib/server/chapters.ts:incrementChapterViews` ниоткуда не вызывается; обновления `releases.view_count` в приложении нет. `app/studio/page.tsx` суммирует значения из релизов и показывает «Просмотров», `ReleaseCard` отображает их же. Следовательно, этот показатель не отражает текущие открытия. Сначала определить смысл просмотра и правила дедупликации, затем ввести один серверный обработчик события и отдельно проверить его на тестовой БД.
3. **P1 — часть форматов не попадает в историю чтения.** `app/vvvvv/[slug]/page.tsx` передаёт `currentUserId` и вызывает `fetchReadingProgress` только для `SpreadReader`; `ReleaseComicReader` и `ReleaseAudioPlayer` не пишут прогресс. Полка `fetchShelf` строится исключительно из `reading_progress`, поэтому эти издания на ней не появляются после просмотра.
4. **P1 — ошибки сохранения скрыты.** `components/spread-reader.tsx` и `components/release-book-reader.tsx` используют `fetch(...).catch(() => {})`, но не проверяют `response.ok`. Ответы 401/400/500 не замечаются клиентом. `keepalive` также не гарантирует подтверждённую запись при уходе со страницы. Нужны обработка статуса, состояние сохранения и безопасный повтор.
5. **P1 — «полка» не является полной историей или библиотекой.** `lib/server/user-profile.ts:fetchShelf` берёт последнюю строку по изданию и ограничивает результат шестью. Она исключает снятые с публикации издания и главы. Отдельных событий посещения, добавления в библиотеку и завершения чтения в этой цепочке нет. Название и интерфейс следует согласовать с фактической семантикой; если нужна история, определить отдельную модель событий.
6. **P2 — нет проверки согласованности главы и издания.** `POST /api/reading-progress` проверяет UUID и процент, но не удостоверяется, что `chapterId` принадлежит `editionId` и опубликован. В тестовой схеме два независимых FK позволяют такую несогласованную пару. Это может давать некорректную полку и восстановление позиции; перед новым ограничением проверить существующие строки production.

## Следующие шаги

Сначала согласовать определения «просмотр релиза», «просмотр главы», «начал читать» и «завершил», а также необходимость истории событий по сравнению с текущим состоянием прогресса. Затем узкими изменениями: добавить согласованную колонку позиции, проверять ответы API, распространить сохранение на нужные форматы и подключить серверный учёт просмотров. На тестовой базе проверить каждый путь синтетическими релизом, изданием, главой и пользователем. Для production подготовить отдельные проверочные SELECT, миграции с откатом и запускать их только после отдельного разрешения.

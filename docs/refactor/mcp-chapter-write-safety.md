# Запись глав через MCP

Исходный коммит `4722ebb685a9943f57e2b53f4768544ddd40404b`, ветка `refactor/phase-2`. Цель прохода — обязательная ревизия в новых контрактах update и restore. Старые клиенты сохраняют имена инструментов, входные параметры и формат результатов.

## Аудит записей

Точка входа — `app/api/mcp/route.ts`. Все инструменты записи глав зарегистрированы в `lib/mcp/tools/chapters.ts` и используют `lib/server/chapters.ts`.

| Инструмент | Запись и проверка |
| --- | --- |
| `canfly_update_chapter_v2`, `canfly_restore_chapter_version_v2` | Сравнивают обязательную ревизию под блокировкой главы до записи главы или истории. |
| `canfly_update_chapter`, `canfly_restore_chapter_version` | Принимают необязательную ревизию. Запрос без неё может перезаписать свежий текст или метаданные. |
| `canfly_publish_chapter` | Меняет `status` и при первой публикации `published_at`. Вызывает `publishChapter(id)` без предусмотренной репозиторием проверки ревизии. |
| `canfly_reorder_chapters` | Меняет `chapter_index` всех глав. Состав проверяется перед транзакцией, ревизии не сверяются. Устаревший список может перезаписать новый порядок, а состав может измениться между проверкой и записью. |
| `canfly_create_chapter` | Вставляет новую главу с исходной ревизией 0. Ревизии существующих глав здесь не нужны. Вставка меняет состав издания и может конфликтовать с будущей транзакцией переупорядочивания. |

Инструменты чтения, поиска и экспорта глав возвращают данные. Инструменты релизов и изданий меняют родительские сущности и связи без записи строк глав. MCP не регистрирует удаление глав, изданий или релизов с каскадом.

## Переход

1. Перевести клиентов update и restore на v2. При конфликте клиент перечитывает главу, сверяет правку и повторяет её с ревизией нового согласованного снимка. Сервер не подставляет актуальную ревизию за клиента.
2. Отдельно согласовать `canfly_publish_chapter_v2` с обязательной ревизией и существующим условным `publishChapter`. Для reorder согласовать версионированный контракт с ID и ревизией каждой главы из исходного списка. Блокировать строки в стабильном порядке, сверять весь состав и все ревизии в одной транзакции до первого UPDATE. Для сериализации изменения состава определить общий протокол блокировок с созданием и удалением глав. Проверить гонки и полный откат.
3. Использовать имеющийся аудит по имени инструмента и исходу. Если нужно отследить именно пропуск ревизии, добавить счётчик вызовов старого контракта по признаку отсутствия поля без содержимого и аргументов. После подтверждения перехода клиентов согласовать и объявить дату отключения. В эту дату отклонять вызовы без ревизии с указанием v2. Удалить устаревшие имена отдельным согласованным изменением после окончания переходного периода. Для публикации и reorder применить тот же процесс после появления их безопасных контрактов.
4. В будущем PR2 проверять право активной сессии на запись по PostgreSQL lease вместе с ревизией в транзакции, которую используют Studio и MCP. Для MCP потребуется идентификатор сессии, способ получения и освобождения lease и явный отказ при чужом или истёкшем lease. Для reorder проверять право записи по всем затронутым главам. До включения lease старые пути должны перестать обходить общую проверку. Ревизия остаётся проверкой актуальности снимка даже при активном lease.

## Проверка и откат

Регрессии проверяют обязательность ревизии, неизменность главы и истории после конфликта, архивацию последующего текста при намеренном восстановлении, совместимость старых вызовов и гонку Studio с MCP. Проверки выполняются на одноразовой PostgreSQL с миграцией PR1. Для отката текущего прохода достаточно вернуть его diff приложения и документации. Контракты прежних инструментов и схема остаются совместимыми.

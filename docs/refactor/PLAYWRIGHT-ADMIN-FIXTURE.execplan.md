## Цель

Каждый запуск Playwright создаёт собственного тестового администратора в изолированной БД. После прогона или восстанавливаемого сбоя удаляются только записи этого запуска. При повторной очистке результат остаётся тем же.

## Затронутые модули

- `playwright.config.ts` — `globalSetup`, `globalTeardown`, адрес и запуск веб-сервера.
- `e2e/setup/global-setup.ts`, `e2e/setup/global-teardown.ts` — создание и очистка.
- `e2e/setup/pg.ts`, `e2e/setup/credentials.ts` — выбор подключения и передача `email`/`userId` воркерам. Потребители включают `e2e/studio.spec.ts` и `e2e/auth-security.spec.ts`.
- `e2e/setup/login-helper.ts` и схема в `postgres/` — прочитать для проверки связанных записей и сценария входа.

## Существующее поведение

Setup делает upsert по `users.login = 'studio_test_admin'`, затем отдельным запросом выдаёт права администратора. Teardown сравнивает `users.login` со строкой `studio-test-admin@canfly.test`, которая является email, и пишет об удалении даже при нуле совпадений. Файл `e2e/.test-credentials.json` удаляется до SQL-очистки. Фиксированные идентификаторы и общий файл позволяют двум запускам перезаписать данные друг друга. Общий конфиг подключает хуки даже для `pnpm test:smoke`.

## Инварианты

- Существующие тесты получают `email` и `userId` администратора, проходят тем же способом входа и с теми же разрешениями.
- Публичное поведение, авторизация приложения, схема БД и конфиги unit и публичных проверок `/v2` сохраняются.
- SQL применяется только к одноразовой тестовой БД. Действия браузера направляются только на тестовый сервер с этой же БД.

Общий конфиг останавливается до запуска сервера и хуков, если в окружении запуска отсутствует `CANFLY_E2E_DATABASE_URL`. Укажи в ней одноразовую локальную PostgreSQL с именем `canfly_e2e_*`, адресом `127.0.0.1` и явным портом. Параметры URL и использование туннеля к удалённой БД исключены из сценария. Хуки и прямые SQL-клиенты сверяют своё подключение с этим адресом. Playwright запускает собственный Next.js на отдельном порту и ждёт сообщение о готовности этого процесса. При занятом порте выбери другой через `PORT`.

## Риски

- **Высокий без изоляции.** Ошибочный URL или переиспользованный dev-сервер может направить записи в рабочую БД. Используй чистую тестовую копию без рабочих файлов окружения, явно переданную одноразовую БД и отдельный локальный порт. Сверь подключения хуков и сервера до запуска.
- **Средний в тестовой среде.** Каскады, остаточные magic-токены и ошибка записи файла могут оставить данные. Проверь фактические внешние ключи и правила удаления, отрабатывай ошибки по идентификаторам конкретного запуска.

## Проход 1 — связать создание и очистку с конкретным запуском

### Проверки до изменений

В отдельной копии исходных хуков подменены клиент `pg` и файловые операции с credentials. Регрессия ожидаемо упала по трём признакам: `INSERT` передавал `studio_test_admin`, а `DELETE` искал `studio-test-admin@canfly.test`; файл исчезал до выполнения SQL; при ошибке SQL teardown завершался успешно.

### Изменения

1. Назначь уникальные login, handle и email в домене `.test` на запуск. Вставляй администратора атомарно, сразу с нужными флагами. Конфликт останавливает создание без обновления существующей записи.
2. Привяжи путь файла credentials к запуску и передай его воркерам. Сохрани интерфейс `loadTestCredentials()`. Публикуй файл после успешной вставки. При ошибке публикации запусти компенсационную очистку по только что полученному UUID.
3. В teardown удаляй по сохранённому UUID и идентификатору фикстуры. Если нужны отдельные удаления, выполни их транзакционно, ограничив записями этого запуска. Если запись уже удалена, повторный teardown завершает удаление файла. При ошибке SQL сохрани файл, сообщи его путь и исходную причину. При аварийном завершении процесса проверь состояние выделенной БД перед повтором.

### Проверки после изменений

1. Из корня выполни `pnpm exec playwright test -c playwright.unit.config.ts tests/unit/playwright-admin-fixture.spec.ts` после добавления этого теста. Покрой создание и удаление по одному UUID, две независимые фикстуры, конфликт с существующим пользователем, ошибку публикации credentials, сбой и повтор очистки. Тест работает с подменёнными зависимостями.
2. Только после подтверждения одноразовой среды выполни `pnpm exec playwright test e2e/auth-security.spec.ts` с изолированным локальным сервером. Проверь по UUID, что тестовый администратор был доступен во время теста и отсутствует после него. Проверь, что контрольная запись сохранилась, а файл этого запуска удалён.

В копии без локальных правок `/v2` прошли все 184 unit-теста. ESLint, TypeScript и `git diff --check` прошли.

### Критерии остановки

Остановись при неподтверждённой изоляции, неизвестном происхождении credentials, неожиданном каскаде, изменении входа или удалении контрольной записи. Не исправляй старые записи в рабочей БД в рамках этого плана.
